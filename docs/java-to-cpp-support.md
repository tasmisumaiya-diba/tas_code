# Java to C++ support audit

CodeBridge currently translates a deliberately restricted Java subset into C++ through the shared IR. The Java compiler frontend attributes the submitted source, but the converter is not a full Java compiler and does not claim to support every Java grammar production or runtime behavior. Accepted syntax is the subset listed below; recognized unsupported constructs are rejected with stable diagnostics, and other unsupported syntax should fail parsing rather than be emitted as successful output.

## Implemented

| Java construct | Current handling |
|---|---|
| Top-level type | One simple top-level class. Primitive instance fields with optional literal initializers convert to a C++ class; uninitialized fields use value initialization to preserve Java defaults. Primitive static fields with literal initializers remain translation-unit globals; `final` maps to `const`. Static methods are emitted as free functions. Instance methods with primitive parameters/return types and supported IR bodies are emitted as C++ class methods; public/private/protected access is retained. The class must be public. |
| Methods | Static methods with supported primitive/`String` signatures use the function IR and are emitted as free functions. Calls written as `ClassName.staticMethod()` lower to the corresponding free-function call when the method is declared static. Instance methods with primitive signatures and supported statement bodies are stored in class IR and emitted as C++ member methods; their access level is preserved. Distinct overloads with supported primitive parameter signatures remain distinct C++ overloads. Instance bodies may use primitive fields and same-class method calls, either unqualified or explicitly through `this.field` / `this.method()`, and may call `System.out.print/println/printf` in supported forms. A bare `this` value and `super` remain unsupported. Java `main(String[] args)` is normalized only when it does not use the command-line argument array. |
| Objects | A local `ClassName object = new ClassName();` declaration for the one supported top-level class lowers to a C++ stack object. Calls such as `object.increment()` are supported when the instance method has a supported primitive signature/body. Reads and writes of public primitive fields (`object.value`) are supported and type-checked. Each declaration creates a separate C++ object. Object alias copies/reassignment and object-valued arguments/returns are diagnosed or rejected. |
| Primitive values | `byte`, `short`, `int`, `long`, `char`, `float`, `double`, and `boolean` in parsed forms. `byte` is represented as `std::int8_t`; Java `long` as C++ `long long`; boolean as C++ boolean. Java `int` and `short` currently use native C++ types and therefore assume the usual 32-bit `int`/16-bit `short` desktop ABI. Compile-time int-to-byte narrowing is accepted only in range. |
| Expressions | Supported literals, names, function calls, array indexing, assignment/compound assignment, increment/decrement, unary operators, arithmetic, comparison, integral bitwise, and logical operators. Boolean `&`, `|`, and `^` are supported when their operands have no side effects; side-effecting operands are rejected because Java guarantees left-to-right evaluation and C++ does not specify the operand order for these operators. Java `String.equals`, `length`, `isEmpty`, `startsWith`, `endsWith`, `contains`, `concat`, and concatenation are supported for the non-null string subset. `String.length()` uses a helper that counts UTF-16 code units for well-formed UTF-8 strings. `Math.sqrt`, `pow`, `floor`, and `ceil` map to `<cmath>` operations and produce a floating-rounding warning; `Math.abs` maps to `std::abs`, with a warning for integral inputs because the minimum value cannot be made positive. The generator adds `<cmath>` when one of these mappings is used. Reference equality (`==`) for strings is rejected because C++ compares string values. |
| Statements | Blocks, local declarations, returns, expression statements, `if/else`, `for`, `while`, `do/while`, `break`, and `continue`. |
| Recursion | Supported-subset static and instance methods can call themselves or other declared methods. Free-function calls resolve supported overloads by argument types; generated C++ declarations are emitted before definitions. Recursion depth and termination remain the program's responsibility, and C++ does not guarantee tail-call optimization. |
| Arrays | One-dimensional supported primitive arrays map to `std::vector`, including runtime-sized arrays and initializer lists. Java's read-only `array.length` maps to `static_cast<int>(array.size())` for C++; using it with the C target is rejected because that target's current array representation has no safe runtime length. Java array indexing emits a warning because the current C++ `operator[]` mapping does not retain Java's bounds exception. `String[]` is accepted only with an explicit initializer list consisting entirely of string literals; Java's default-null array elements and null entries are rejected. `char[]` and multidimensional arrays are rejected. |
| Console output | `System.out.print`/`println` support strings, byte/short/int/long, float/double, char, and boolean values. Java boolean output uses `std::boolalpha` so the visible output is `true`/`false`; ordinary output uses idiomatic `std::cout` streams. Unsupported formatting/type combinations are diagnosed. |
| Console input | One local `Scanner` initialized with `new Scanner(System.in)` maps to C++ `std::cin`. Matching `int`/`long`/`float`/`double` declarations using `nextInt()`/`nextLong()`/`nextFloat()`/`nextDouble()`, and `String` declarations using `next()` or `nextLine()`, lower to `std::cin` token reads or `std::getline`. Multiple Scanner objects are rejected with `CB-JAVA-SCANNER-MULTIPLE-UNSUPPORTED` because their independent Java buffers cannot be preserved by one C++ stream. A `close()` after the final read is removed; a later read after Scanner close is rejected with `CB-JAVA-SCANNER-CLOSED-READ`. Other Scanner methods and mismatched types receive an unsupported diagnostic. String input is C++ only; C target conversion reports an unsupported Scanner diagnostic. |
| Validation | Generated C++ is passed to the compiler validation service when `g++` is available. Docker output comparison is a separate opt-in validation path; compilation alone does not prove behavioral equivalence. |

Java 21 grammar parsing is provided by `codebridge-lang-java/.../JavaAstFrontend.java` using the JDK compiler tree API. It produces a structural index and shared recursive `TypeReference`/`TypeParameter` IR values for packages, imports, declarations, generic bounds, and method signatures. The lowering stage still accepts only the subset described above; parsing a Java construct is not a claim that the converter can lower it. Java String-to-C++ operation mappings are read from `codebridge-rules/src/main/resources/java-cpp-runtime-mappings.tsv`; the prefix, suffix, and containment mappings emit small C++ runtime helpers. The subset parser/generator are in `codebridge-core/.../SubsetFunctionParser.java` and `SubsetFunctionGenerator.java`, and C++ generation is in `codebridge-lang-cpp/.../CppGenerator.java`. Positive conversions, C++ compile checks, and negative diagnostics are covered by `CodeBridgePipelineTest` and the integration tests.

## Runtime differences and diagnostics

- Java `byte` and `long` have explicit fixed-width C++ representations. `int` and `short` use native C++ types and assume a mainstream desktop ABI with 32-bit `int` and 16-bit `short`.
- Java signed integer arithmetic wraps on overflow; signed C++ overflow is undefined. Java-to-C++ integral arithmetic, unary negation, and increment/decrement emit `CB-JAVA-CPP-INTEGER-OVERFLOW-POSSIBLE` warnings. Keep those operations in range or verify the result for the intended inputs.
- Java integral division/remainder by zero throws `ArithmeticException`; C++ has undefined behavior. A literal zero divisor is rejected with `CB-JAVA-CPP-DIVIDE-BY-ZERO`, and a non-literal integral divisor emits `CB-JAVA-CPP-DIVISOR-MAY-BE-ZERO` unless it is a recognized non-zero numeric literal.
- Java masks integer shift distances to 5 bits (`int`) or 6 bits (`long`); C++ shift counts must be non-negative and less than the promoted left operand width. Recognized Java `<<` and `>>` expressions emit `CB-JAVA-CPP-SHIFT-DISTANCE`; keep the distance in range.
- Java `char` is a 16-bit UTF-16 code unit while C++ `char` is a byte. Uses emit `CB-JAVA-CPP-CHAR-WIDTH`; only values representable in the target execution character set are safe. `char[]` remains unsupported.
- Java array access throws on invalid indexes; current C++ output uses unchecked `std::vector::operator[]`. Each recognized Java array access emits `CB-JAVA-CPP-ARRAY-BOUNDS`; keep all indexes within `[0, array.length)`.
- Java strings are modeled as UTF-8 `std::string`. The `length()` helper reproduces Java UTF-16 code-unit counts for well-formed UTF-8, including supplementary code points. Lone surrogates, malformed runtime input encodings, and locale-specific console encoding differences are not guaranteed.
- The accepted subset avoids general Java object aliasing and identity. Unsupported object/reference features, `null`, and arbitrary Java libraries are diagnosed instead of translating garbage collection into C++ ownership behavior. Scanner instances are flattened to `std::cin`; their independent buffering and close behavior are not preserved.
- The mapped `<cmath>` calls can differ from Java at floating-point rounding boundaries; a warning is emitted. Other Java library calls remain unsupported unless mapped explicitly.

## Explicitly unsupported or restricted

- Packages, imports other than the narrow `java.util.Scanner` console-input case, multiple top-level declarations, annotations, records, sealed declarations, native methods, and arbitrary modifiers.
- Object behavior remains restricted: local no-argument construction of the supported class is lowered to a separate stack object. Explicit empty no-argument constructors with explicit public/protected/private access are preserved, but parameterized constructors and constructors with initialization logic are diagnosed. Object aliasing/copying, object-valued parameters or returns, private/protected field access from outside the class, bare `this`, `super`, inheritance, interfaces, dynamic dispatch, nested classes, and non-literal field initializers are unsupported. Primitive instance methods can read/write primitive fields and call same-class methods using unqualified names or `this.member`; basic `System.out` output is supported, while other Java library calls are not. C++ stack lifetime replaces JVM garbage collection only for this isolated local-object subset.
- Generics and collections; lambdas and method references; `var`; object allocation; `null`; switch statements/expressions; enhanced-for loops; exceptions; synchronization and threading.
- Java unsigned right shift (`>>>`) is rejected with `CB-JAVA-UNSIGNED-SHIFT-UNSUPPORTED`; the current IR has no explicit unsigned bit-width conversion model for preserving Java's fixed-width result.
- Multidimensional arrays, `char[]`, and `String[]` without a fully explicit non-null literal initializer.
- Arbitrary Java library APIs, reflection, annotations processors, serialization, streams, and JVM-specific behavior. String helpers model the documented subset only; Java UTF-16 behavior for arbitrary Unicode strings is not guaranteed by `std::string`.
- The frontend parses Java 21 syntax, but its current conversion lowering does not model most of the features below. The Java and C++ type systems are not identical. In particular, UTF-16 `char` and Java string indexing/length semantics cannot be assumed equivalent to native C++ `char`/`std::string` for arbitrary Unicode data. The current implementation's scalar char and string support is a constrained convenience subset, not a guarantee for every Unicode input.

## What “complete Java syntax” would require

“All Java syntax” is not a finite add-on to this parser. Full support requires a Java grammar and semantic frontend, symbol/type resolution, a substantially richer IR (classes, object identity, overload resolution, generics, exceptions, arrays, and library/runtime models), and target runtime shims where C++ has no direct equivalent. Every syntax family then needs positive, negative, compiler, and behavior-equivalence tests. Until those pieces exist, this page is the supported contract; rejected or unparsed Java must not be reported as converted.
